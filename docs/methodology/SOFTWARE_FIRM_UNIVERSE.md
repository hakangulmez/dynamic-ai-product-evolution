# Software-Firm Universe Construction Methodology

## Status

**Draft for sentinel implementation and validation.**

This document is the canonical methodological definition of the firm universe for the Dynamic AI Product Evolution project. It governs the construction of the historical SEC filer frame, the multi-axis classification of firms, the derivation of confirmatory and extension samples, the treatment of entry and exit, and the universe freeze process.

The universe is constructed before product, capability, task, or measurement extraction. Later AI adoption, product transformation, financial performance, or survival outcomes must never determine whether a baseline firm enters the main incumbent cohort.

## 1. Why universe design is a first-order research decision

The study does not ask whether every company uses software. Nearly all modern firms do. It asks how companies whose customer value is materially delivered through software-led products changed their product-task systems during the frontier-LLM transition.

A broad label such as `technology company`, a software SIC code, or the presence of an application is not sufficient. Three firms may all operate digital interfaces while producing fundamentally different customer outcomes:

```text
Enterprise workflow application
→ software itself produces and executes the customer's work outcome

Ride-hailing marketplace
→ software coordinates a driver and a physical transport service

Streaming service
→ software distributes a licensed or produced content catalogue
```

These businesses face different substitution frontiers, complementary assets, task ontologies, and outcome mechanisms. Mixing them without classification would confound software functionality with physical networks, licensed content, attention markets, regulated transaction rails, or human service delivery.

The project therefore does not create one opaque `software_firm = true/false` label. It records separate economic dimensions and derives versioned analytical samples from explicit rules.

## 2. Target population

The broad economic population is:

> Public operating firms whose externally offered customer value is wholly or materially delivered through an interactive software or software-led digital product.

The initial confirmatory population is narrower:

> Domestic SEC annual-report filers that were publicly listed by the baseline cutoff and whose core or material customer outcome was generated by a functional software, adaptive digital service, or functional data-and-analytics product.

The target definition is economic rather than keyword-based. A firm can qualify even when its SEC SIC code is outside the conventional software family. Conversely, a firm does not qualify merely because it uses AI, has a mobile application, calls itself a platform, or has a software subsidiary.

## 3. Baseline cohort and temporal rule

### 3.1 Ex-ante incumbent cohort

The main incumbent cohort is defined using the last eligible annual filing on or before the project baseline cutoff. The cutoff will be frozen in `configs/project.yaml` and recorded in every universe manifest.

Baseline inclusion uses only information available on or before that cutoff. Post-baseline product pages, later AI pivots, later success, later failure, or current index membership cannot affect incumbent eligibility.

This protects against:

- survivorship bias;
- selecting firms because they later became prominent AI winners;
- excluding firms that were acquired, delisted, bankrupt, or unsuccessful;
- post-treatment sample selection;
- reconstructing a historical universe from current ticker lists.

### 3.2 Entrant cohort

Firms entering public markets after the baseline are retained in a separate entrant cohort. Entry types include:

- initial public offering;
- direct listing;
- completed de-SPAC operating-company entry;
- spin-off;
- newly eligible annual filer.

Entrants may be used in descriptive product-transition analyses. They are not automatically pooled with the balanced incumbent cohort in analyses requiring a pre-baseline observation.

### 3.3 Exit events

Acquisition, merger, delisting, bankruptcy, liquidation, and cessation of reporting end future standalone observations but do not remove prior observations.

An acquired firm's products are not automatically transferred to the acquirer. Product lineage requires dated evidence of acquisition closing and integration or continuation.

## 4. Multi-axis classification model

Every candidate firm is classified on four independent economic axes. These fields are observations, not final sample decisions.

### 4.1 Customer-value archetype

This axis describes what the customer is fundamentally purchasing. It is multi-label because diversified firms can contain several material product systems.

| Code | Definition | Typical economic mechanism |
|---|---|---|
| `FUNCTIONAL_SOFTWARE` | Software directly enables or executes a work outcome | create, analyze, manage, design, secure, automate, or operate |
| `ADAPTIVE_DIGITAL_SERVICE` | The system produces an individualized digital result in response to a user need | tutoring, writing support, personalized learning, generated advice |
| `DATA_ANALYTICS_PRODUCT` | Software searches, combines, analyzes, monitors, or operationalizes data for customer decisions | financial information systems, risk analytics, scientific databases |
| `TRANSACTION_INFRASTRUCTURE` | The product authorizes, routes, records, reconciles, or secures a digital transaction | payment and regulated transaction systems |
| `MARKETPLACE_COORDINATION` | The software matches or coordinates separate market participants or physical supply | ride, lodging, delivery, labor, or goods marketplaces |
| `CONTENT_CATALOG` | The primary value is access to licensed, owned, or produced media/content | streaming audio/video and catalogue subscriptions |
| `ATTENTION_SOCIAL_PLATFORM` | The core system creates user interaction, attention inventory, and network participation | social and advertising-supported platforms |
| `INTERACTIVE_ENTERTAINMENT` | The main customer outcome is participation in a game or interactive entertainment environment | games and virtual worlds |
| `HARDWARE_SOFTWARE_SYSTEM` | The outcome requires a coupled device, machine, or physical system | medical, industrial, communications, or device ecosystems |
| `HUMAN_MANAGED_SERVICE` | Employees or contractors remain the primary delivery mechanism | consulting, outsourcing, managed professional services |
| `ECOMMERCE_RETAIL` | The core outcome is purchase and delivery of physical goods | online retail and logistics |
| `PHYSICAL_SERVICE_NETWORK` | The final customer outcome is a physical service | transport, delivery, care, or field service |
| `OTHER` | None of the above is adequate | requires review and a written definition |

The archetype is assigned from explicit customer-product evidence. Industry labels and company self-descriptions are secondary signals.

### 4.2 Software centrality

This axis asks how software contributes to the customer outcome.

| Code | Definition |
|---|---|
| `CORE` | Software is the primary mechanism that produces the customer-facing result. |
| `CO_ESSENTIAL` | Software is necessary, but another asset is equally necessary to produce the result. |
| `ENABLING` | Software mainly provides access, coordination, distribution, or a transaction interface to another underlying asset or service. |
| `PERIPHERAL` | Software is ancillary to the main commercial outcome. |
| `UNKNOWN` | Evidence is insufficient or contradictory. |

Examples of the distinction:

```text
Document editing application
software_centrality = CORE

Financial analytics terminal using licensed market data
software_centrality = CO_ESSENTIAL

Ride-hailing application coordinating drivers and vehicles
software_centrality = ENABLING

Retailer's customer mobile application
software_centrality = PERIPHERAL or ENABLING, depending on the business model
```

### 4.3 Necessary complementary dependencies

Dependencies record assets required to deliver the task. Multiple values are allowed.

- `NONE_OR_STANDARD_COMPUTE`
- `CUSTOMER_DATA`
- `FIRM_PROPRIETARY_DATA`
- `LICENSED_DATA`
- `LICENSED_CONTENT`
- `NETWORK_OR_INSTALLED_BASE`
- `REGULATED_TRANSACTION_RAIL`
- `EXECUTION_PERMISSIONS`
- `HARDWARE_OR_DEVICE`
- `PHYSICAL_SUPPLY_NETWORK`
- `LIVE_HUMAN_LABOR`
- `SPECIALIZED_NON_LLM_ENGINE`
- `OTHER`

The existence of a dependency is not a defensibility score. A large proprietary corpus, network, or specialized engine may or may not prevent frontier substitution for a particular customer task. Defensibility is measured later at the task level using an explicit counterfactual.

### 4.4 Firm structure and materiality

This axis determines whether product-level observations can be linked cleanly to firm-level outcomes.

| Code | Definition |
|---|---|
| `PURE_PLAY` | Nearly all material activity belongs to the eligible digital-product system. |
| `SOFTWARE_DOMINANT` | The firm has multiple activities, but software-led products clearly dominate. |
| `MIXED_SEPARABLE` | An eligible software business is material and has a separately observable segment or economic reporting unit. |
| `MIXED_NONSEPARABLE` | Eligible software activity is material but cannot be separated reliably from other businesses in firm-level outcomes. |
| `SOFTWARE_PERIPHERAL` | Software is a minor or supporting commercial activity. |
| `UNKNOWN` | Materiality cannot be established from the baseline packet. |

Commercial materiality is recorded separately as `DOMINANT`, `MATERIAL`, `MINOR`, or `UNKNOWN`.

A valid product-level software observation does not by itself create clean firm-level financial identification. Mixed and nonseparable firms remain useful for descriptive product analysis but require separate treatment in outcome regressions.

## 5. Derived analytical tiers

Tiers are derived from the stored axes by versioned rules in `configs/universe_sample_rules.yaml`. The classifier does not directly determine the final sample.

### 5.1 Tier A — Core confirmatory sample

Provisional Tier A eligibility requires:

- operating company and eligible annual filer;
- baseline-dated customer-facing evidence;
- at least one material archetype among:
  - `FUNCTIONAL_SOFTWARE`;
  - `ADAPTIVE_DIGITAL_SERVICE`;
  - `DATA_ANALYTICS_PRODUCT` when software performs the analytical customer task;
- software centrality `CORE` or strong `CO_ESSENTIAL`;
- firm structure `PURE_PLAY` or `SOFTWARE_DOMINANT`;
- commercial materiality `DOMINANT` or `MATERIAL`;
- sufficient evidence for at least one Product → Capability → Task chain;
- no unresolved shell, fund, or issuer-status exclusion.

Tier A is the cleanest confirmatory sample. It may contain separate reported strata such as core enterprise software, consumer adaptive digital services, and data/analytics products.

### 5.2 Tier B — Functional digital extension

Tier B retains economically relevant but less homogeneous cases, including:

- transaction infrastructure;
- regulated digital systems;
- data-heavy products with strong non-software dependencies;
- `MIXED_SEPARABLE` firms with an identifiable software segment;
- software/hardware systems where the software task can be studied separately;
- firms with material human-service overlays.

Tier B supports mechanism comparison and robustness analysis. Inclusion in a firm-level outcome model requires a documented mapping from product or segment exposure to the relevant financial outcome.

### 5.3 Tier C — Boundary and negative-control sample

Tier C retains digital firms whose core outcome is primarily mediated rather than produced by software, including:

- physical marketplaces and service networks;
- content catalogues;
- attention/social platforms;
- games and interactive entertainment;
- e-commerce and retail systems;
- hardware-heavy systems;
- human-managed services;
- mixed nonseparable conglomerates.

Tier C is not discarded. It is essential for testing whether the universe classifier simply labels every digitally mediated company as software. It also permits later extension studies with mechanism-specific task definitions.

### 5.4 Excluded and uncertain records

`EXCLUDED` is reserved for records that fail explicit economic or issuer rules. `UNCERTAIN` is a valid outcome and must not be forced into include/exclude.

Economic eligibility and data eligibility are separate:

```text
economically_eligible = true
data_eligible = false
```

means the firm fits the target concept but lacks sufficient historical evidence for production extraction. Such firms remain in coverage and missing-data reports.

## 6. How the universe is constructed from SEC EDGAR

The project uses the full eligible historical annual-filer frame as the discovery base. It does not ask one model to browse all EDGAR filings and return a software-company list.

### 6.1 Stage 00A — Historical annual-filer frame

Create a dated CIK-level table from SEC filing history. The initial domestic frame includes operating-company annual reports such as `10-K` and `10-KT`; amendments are linked to the original filing rather than counted as new observations.

The frame must preserve:

- CIK as the stable firm identifier;
- legal and former names;
- historical ticker and exchange when available;
- accession number and filing date;
- fiscal year end;
- form type;
- SIC at the observation date;
- filing and cover-page locations;
- entry and exit status.

Current ticker lists are not historical ground truth. Baseline listing and issuer status require dated evidence.

Foreign private issuers (`20-F`, `40-F`) are initially retained as an extension frame and are not silently mixed with domestic `10-K` observations.

### 6.2 Stage 00B — Deterministic issuer exclusions

Before model classification, remove or separately flag clear non-operating entities:

- mutual funds and exchange-traded funds;
- registered investment companies where the filing is a fund report rather than an operating business description;
- asset-backed issuers;
- trusts without an operating business;
- blank-check and shell companies before a completed business combination;
- duplicate share classes and duplicate issuer records;
- entities without an eligible annual operating report.

Every exclusion requires a reason code. No record is silently dropped.

### 6.3 Stage 00C — Baseline evidence packets

For every remaining CIK, construct a compact baseline packet from dated SEC evidence. The default packet contains:

- company and filing metadata;
- Item 1 overview/business description;
- product and service subsections;
- customer description;
- material revenue or segment description;
- selected technology/platform passages where they clarify delivery;
- cover-page evidence needed for issuer and listing status.

The universe packet is intentionally narrower than the later product corpus. Live or post-baseline product pages cannot establish baseline eligibility.

### 6.4 Stage 00D — High-recall screen

A low-cost, high-recall model pass asks whether the filing plausibly describes a material customer-facing functional digital product. It returns:

- `LIKELY_ELIGIBLE`;
- `LIKELY_INELIGIBLE`;
- `BOUNDARY_OR_UNCERTAIN`.

The first pass is not the final classifier. Its purpose is to reduce cost while preserving recall.

### 6.5 Stage 00E — Full multi-axis classification

All positive and uncertain candidates receive the full taxonomy classifier. The classifier emits evidence-backed observations for the four axes, confidence, contradictions, and boundary flags.

It must not infer eligibility from:

- software or AI keywords;
- a mobile application;
- an internal technology stack;
- generic platform language;
- current product pages;
- later financial or AI outcomes;
- SIC or NAICS alone.

### 6.6 Stage 00F — Rule-based tier derivation

A deterministic rules engine applies the versioned sample rules. This separation ensures that a prompt revision cannot silently redefine the analytical population.

### 6.7 Stage 00G — Manual boundary adjudication

Manual review is required for:

- conflicting archetypes or centrality judgments;
- `CO_ESSENTIAL` cases near Tier A/Tier B;
- marketplaces, content, games, payments, and data platforms;
- mixed firms and segment-materiality disputes;
- hardware/software hybrids;
- services-heavy firms;
- insufficient or contradictory evidence;
- cases where the model's proposed tier conflicts with deterministic rules.

Review decisions are append-only and preserve the original model output.

### 6.8 Stage 00H — Negative-sample audit

A stratified random sample of first-pass negatives must be manually audited. Strata should include SIC family, firm size where available, industry family, filing year, and unusual textual candidates.

The negative audit estimates false-negative risk. A universe cannot be frozen solely from precision among selected positive candidates.

### 6.9 Stage 00I — Universe freeze

The release is frozen as `UNIVERSE_vX.Y` only after hard validation gates and sentinel thresholds pass. The freeze manifest records:

- baseline cutoff and form scope;
- candidate-frame hash;
- deterministic-exclusion rules;
- packet-construction version;
- classifier prompt and model versions;
- schema and taxonomy versions;
- sample-rule version;
- gold, adversarial, and negative-audit results;
- manual-review completion;
- included, excluded, uncertain, and data-ineligible counts;
- unresolved limitations.

Downstream product extraction consumes a frozen universe release, never an unversioned working list.

## 7. Identity, entry, exit, and lineage

### 7.1 Stable identity

CIK is the primary issuer identifier. Ticker is a dated attribute, not the primary key. Multiple share classes belonging to one operating company are consolidated at the CIK level unless a specific research design requires security-level observations.

### 7.2 Name and ticker changes

Former names and ticker histories are preserved. A change in name or ticker does not create a new firm unless SEC/legal lineage indicates a new operating entity.

### 7.3 Mergers and acquisitions

The standalone target remains observable through the closing date. The acquirer and target are linked in `firm_lineage`. Products are transferred only when official evidence supports continuation or integration.

### 7.4 Spin-offs

A spin-off creates a new firm record with a lineage relation and effective date. Pre-spin observations remain associated with the predecessor unless product lineage is separately reconstructed.

### 7.5 De-SPAC events

A pre-combination blank-check company is not an operating-company observation. The operating company may enter the entrant cohort after the business combination becomes effective and an eligible operating filing is available.

## 8. Data model

The canonical universe layer consists of four tables.

### 8.1 `company_universe_classifications`

One baseline classification record per candidate firm and universe version. It stores the economic axes, evidence, classifier output, rule-derived tier, and review state.

### 8.2 `firm_year_eligibility`

One record per firm and annual observation. It stores public/operating status, form, entry/exit type, annual eligibility, and cohort status.

### 8.3 `firm_lineage`

Dated merger, acquisition, spin-off, predecessor, successor, and name-change relations.

### 8.4 `universe_run_manifest`

Complete provenance for candidate generation, screening, classification, adjudication, negative audit, and freeze.

The base `company` table remains a stable identity registry and does not absorb all time-varying classification fields.

## 9. Evaluation design

Universe classification has its own eval harness before product extraction begins.

### 9.1 Gold strata

The gold set must include:

- clear core software firms;
- adaptive consumer digital products;
- data and analytics firms;
- transaction infrastructure;
- marketplaces and physical service platforms;
- content catalogues;
- social/attention platforms;
- games;
- hardware/software hybrids;
- professional services firms;
- banks, retailers, manufacturers, and other software-enabled non-software controls;
- mixed and diversified firms.

The gold set must not be dominated by firms previously used in prompt development.

### 9.2 Metrics

Report at minimum:

- high-recall screen recall;
- Tier A precision and recall;
- customer-value archetype agreement;
- software-centrality agreement;
- firm-structure agreement;
- materiality agreement;
- false inclusion of software-enabled non-software firms;
- false exclusion identified in the negative audit;
- evidence validity;
- temporal leakage;
- unresolved/unknown rate;
- reviewer agreement on boundary cases.

### 9.3 Hard gates

The following are release blockers:

- future-dated evidence used for baseline classification;
- evidence-free inclusion;
- fabricated or unresolved evidence quote;
- fund, shell, or non-operating entity entering Tier A;
- unknown forcibly converted to include or exclude;
- duplicate CIK in the frozen identity table;
- silent removal of exited or failed firms;
- missing run manifest or taxonomy version.

Numeric pilot thresholds are provisional until the gold set is built. Threshold changes require a decision-log entry and a versioned change request.

## 10. Sentinel implementation plan

The first sentinel should include approximately 30–40 deliberately heterogeneous firms:

- clear Tier A core software;
- adaptive digital-service boundary cases;
- data/analytics and payment infrastructure;
- mixed and hybrid firms;
- marketplaces, content platforms, and games;
- obvious non-software controls;
- difficult issuer and lineage cases.

The sentinel objective is not to estimate the universe size. It is to identify taxonomy failures, packet insufficiency, false positives, false negatives, and review workload.

Only after the sentinel passes should the high-recall screen be run across the historical annual-filer frame.

## 11. Decisions that remain open

The following are intentionally not frozen before the sentinel:

- exact baseline cutoff date;
- whether Tier A includes all `DATA_ANALYTICS_PRODUCT` firms or only software-dominant cases;
- treatment of certain transaction-infrastructure firms;
- minimum evidence packet coverage;
- quantitative recall and precision thresholds;
- whether foreign private issuers enter the first release or a later extension;
- exact materiality rule for mixed firms;
- source used to validate historical exchange status where SEC cover-page evidence is incomplete.

Open decisions must not be resolved implicitly in code or prompt wording.

## 12. Canonical principle

The universe is not “all firms that mention software.” It is a dated, evidence-backed economic classification of how customer value is produced.

```text
Historical SEC annual-filer frame
→ deterministic issuer cleaning
→ baseline evidence packets
→ high-recall screening
→ multi-axis classification
→ rule-based Tier A/B/C derivation
→ boundary adjudication
→ negative-sample audit
→ versioned universe freeze
```
